# 数据流详细设计（现网对齐版）

## 1. 控制面通用数据流

```
前端 ──HTTP──▶ middleware（限流/CORS/JWT/Idempotency） ──▶ handler ──▶ service ──▶ repository ──▶ DB
                                                                       │
                                                                       └──▶ k8s/helm/grafana/vm/logagent/notify
```

每条业务请求：

1. 限流 → 认证 → 角色断言（必要时）
2. handler：参数绑定 + **工作空间** / 资源所有权断言
3. service：业务规则、外部调用、审计
4. 写操作命中幂等存储 → 返回缓存结果

## 2. 平台扩容数据流

### 2.1 dry-run

```
admin POST /platform/scaling/vmcluster {target_id, spec, dry_run:true}
  → PlatformService.Plan（校验注册目标、渲染 spec_patch）
  → audits status=success
```

### 2.2 apply

```
admin POST ... dry_run=false + Idempotency-Key
  → Idempotency.SetNX（命中则重放）
  → K8s MergePatch VMCluster.spec
  → audits + 缓存响应
```

## 3. 接入中心数据流

### 3.1 Plan / Install / Uninstall

与既有流程相同：`install/plan` 只渲染 diff；`install` 处理 install/upgrade/reinstall；`DELETE installations/:id` 按 label 删除资源并软删。

请求体中的 `tenant_id` 为 **残余字段名**，语义为所属 Workspace UUID，必须与目标监控实例一致。

资源标签：`managed-by=ops-system` / `template=<id>` / `installation=<id>`。

### 3.2 模板版本 / 模板删除

活跃安装引用 → 409；最后一版本不可删；模板软删释放 name。

## 4. Workspace VM Provisioning

```
admin POST /workspaces {name, ...}
          │
          ▼
WorkspaceService.Create
   1. 写 ops_workspaces
   2. Grafana CreateOrg（最佳努力）→ 记录 org 映射
   3. WorkspaceProvisioner.ProvisionCreate
          ├─ vm_routes：RouteBuilder → ops_vm_routes
          ├─ vm_operator_user：ApplyTenantUser（历史方法名）→ Secret + VMUser
          └─ default_datasource → ops_datasources
```

要点：各步 `ProvisioningTask` 最大努力；K8s 不可用时 Operator 步骤可降级 noop。

## 5. 业务集群采集配置数据流

```
创建业务集群
  → 默认 MetricsCollectConfig / LogsCollectConfig 入库
  → 按 metrics 配置渲染并 Apply VMAgent（remoteWrite + U-001 标签）

PUT /business-clusters/:id/collect-config
  → 更新 JSONB
  → 重新渲染 VMAgent；若日志已启用则同步 Vector

POST .../enable-logs
  → 按 LogsCollectConfig 部署 Vector Agent → Kafka → 聚合 → VictoriaLogs
POST .../disable-logs
  → 拆除日志采集资源
```

**MetricsCollectConfig**：抓取间隔/超时、命名空间 include/exclude、`select_all_by_default`  
**LogsCollectConfig**：命名空间过滤、`exclude_paths`

查询侧 LogsQL 强制按工作空间标签过滤（标签键可能仍为 `ops_tenant_id`）。

## 6. 告警数据流

### 6.1 规则创建 / 导入

```
POST /alerts/rules  或  POST /alerts/rules/import (multipart file + tenant_id)
  → 解析 Prometheus groups（跳过 recording / 重复）
  → 写入 ops_alert_rules
  → ApplyAlertRule → VMRule CR
```

### 6.2 事件

```
Alertmanager → POST /webhooks/alertmanager
  → AlertEventService 入库
  → 可选 notify 渠道
前端 PUT /alerts/events/:id/ack → 确认
```

## 7. 指标库解析数据流

模板版本变更 → `metric_parser_service` 从 collector / dashboard / alert spec 抽取指标 → upsert `ops_metrics` + mappings；`manual_override=true` 跳过覆盖。`POST /metrics/reparse/:templateId` 可重跑。

## 8. 审计查询

`GET /platform/scaling/audits` 与 `GET /audits`（admin）：分页、筛选、按时间倒序。

## 9. 一致性原则

- **可追溯优先**：成功/失败/拒绝都落审计
- **幂等不重放外部副作用**
- **工作空间隔离 in service**：repository 不假设调用方已过滤
- **字段双轨**：API 优先 `workspace_id`；部分 JSON/列仍用 `tenant_id`（同 UUID）
- **软删边界**：业务表软删；审计表不软删
